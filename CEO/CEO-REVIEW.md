## Problem Statement

Claude Code users have a buddy character in their terminal — a named, species-specific
companion (mushroom, dragon, cat, etc.) that exists only as ASCII art and text.
There's no visual, no personality beyond a name, and no social layer. The Buddy App
takes that character and makes it real: a living animated desktop pet that watches
your coding activity, responds to you through Claude's API, and — in MVP2 — lets you
fight other developers' buddies in a Pokemon Go-style arena.

## What Makes This Cool

Three compounding layers:

1. **Visual identity** — Your buddy is actually *yours*. Duolingo-quality Rive animation,
   custom-designed on Fiverr for your species (mushroom, dragon, etc.), baby → teen → adult
   growth stages. People will screenshot this and share it.

2. **Office productivity** — Claude Code power in a GUI. Talk to your buddy via text or
   WhatsApp-style voice recording, get Claude responses streamed back. It lives on your
   desktop while you work. Not a replacement for the terminal — a companion to it.

3. **Fight arena (MVP2)** — Pokemon Go for the dev community. Your buddy's stats come
   from real coding activity: git commits, Claude Code session time, XP from feeding.
   Grind code = grind your fighter. Share a buddy code to fight friends. Long-term:
   public leaderboard where the whole community can challenge each other.

The fight arena is the retention mechanic that makes everything else matter. It gives
developers a reason to leave the app open all day — because every hour of coding is
leveling up their fighter.

## Constraints

- App is Tauri (not Electron) — ~15MB RAM, right for a developer audience that hates bloat. buddy2 is a Tauri rewrite of the Electron buddy prototype; the Electron codebase at ~/buddy is not used.
- Character species is read from `~/.claude/` — whatever the user has set in Claude Code
- All visual assets are Fiverr-designed Rive animations — no emoji, no Three.js primitives
- MVP1 has no backend — everything is local + Claude API calls
- Window: 300×460px, transparent, floating desktop widget

## Premises

1. Buddy species/name is read from `~/.claude/` — no custom picker in the app for MVP1
2. Fight stats come from real coding activity (git, Claude Code sessions, feeding XP)
3. Fiverr Rive animations are the character system — custom designed, hand-animated
4. Tauri not Electron — footprint matters for this audience
5. MVP1 ships without a backend — local only + Claude API

## Approaches Considered

### Approach A: Sequential Layers (CHOSEN)
Ship MVP1 (character + office) fully polished. Then build arena on top of a
community that already loves the pet. Each layer independently shippable.
- Effort: M (MVP1) then L (MVP2)
- Risk: Low
- Pros: Community builds around the pet before arena exists. Fiverr assets have
  time to be made properly. Office room has time to feel polished.
- Cons: Arena takes longer

### Approach B: Parallel Skeleton
Build rough arena mechanic with placeholder art simultaneously with MVP1.
- Risk: Medium — splits focus, MVP1 quality suffers

### Approach C: Arena-First Skeleton
Get one fight working with 2 placeholder buddies first, then polish everything.
- Risk: Medium-High — office + character feel half-baked when showing it

## Recommended Approach

**Approach A — Sequential layers.**

The character + office need to be good enough that devs keep the app open all day.
If they keep it open, their buddy gains XP naturally from coding activity. When
the arena ships, their buddy is already leveled and they're invested. Splitting
focus now produces two mediocre things instead of one great one. Nail MVP1, then
the arena launches into an audience that's already attached to their character.

## MVP2 Build Plan — Fight Arena

### Arena stat system
Each buddy has 4 derived stats from real activity:
- **HP** = total XP / 10 (capped at 500)
- **Attack** = git commits last 30 days * 2
- **Defense** = hours the Buddy app was open while git commits were happening (proxy for active coding sessions; no Claude Code process detection needed)
- **Speed** = feeding consistency (daily streak)

### Share code format
Export buddy as a signed JSON blob (base64):
```
{
  name: string,
  species: string,
  stage: "baby" | "teen" | "adult",
  stats: { hp, attack, defense, speed },
  cosmetics: { colors[], accessories[] },  // ship as empty arrays in MVP2; cosmetics system is post-MVP2
  checksum: sha256(name + species + stage + hp + attack + defense + speed)  // tamper-evident, not tamper-proof; stats are frozen at export time
}
```
Share as a QR code or copy-paste string. Opponent imports it to fight locally.

### Battle mechanic (turn-based)
- Turn order by Speed stat
- Each turn: Attack / Defend / Special (unlocked at teen/adult)
- Damage = attacker.attack * random(0.8, 1.2) - defender.defense * 0.5
- Winner gets XP bonus, loser gets consolation XP
- Animations: attack/hurt/faint states in Rive character

### Post-MVP2 / Community Layer (out of scope for MVP2 sprint)
- Backend: simple API (Cloudflare Workers or Supabase)
- Register buddy with public key
- Post fight results (both players sign)
- Global leaderboard by win rate + total XP
- Browse and challenge other buddies in-app
MVP2 ships local-only peer fights via share code. The community layer is a separate sprint once share-code fights are proven fun.

## Success Criteria

MVP1 (character + office):
- A Claude Code developer keeps the app open for a full workday
- They send at least 3 messages to their buddy in the Office room
- Someone screenshots the character and shares it in a dev community
- The character visually matches their Claude Code buddy species

MVP2 (arena):
- Two developers fight each other's buddies using share codes
- The loser wants a rematch
- Someone posts their win to Twitter/X
